# Skill changes

Repo maintenance. Build agents do not read this document.

What should change in the `vibedata-data-engineering` plugin, found while porting this repo to a Fabric Lakehouse. Paths in the Reference column are relative to the plugin root. The rows inherited from building the DuckDB repo are in that repo's [`docs/setup/skill-changes.md`](https://github.com/accelerate-data/sample-nyctaxi-comp/blob/main/docs/setup/skill-changes.md). The `.agents/skills/workarounds` rules point here when the plugin gap they cover is specific to Fabric.

| Skill | Reference | Suggested change | Status |
| --- | --- | --- | --- |
| `fabric_lakehouse` dbt | `_shared/platforms/fabric_lakehouse/dbt.md` § Sandbox run | Name the full sandbox command: plain `dbt` (the image's `dbt` loads the Intent's coordinates itself, so no wrapper), `--target ephemeral_dev` and `--defer --state /cache/prod-target`. Until then `.agents/skills/workarounds` states it. | shipped: `dbt.md` states the target, `--defer` and the path selection, and the plugin installs declared packages before the first dbt command (VD-7411); the `workarounds` rule is removed (VD-7428) |
| `fabric_lakehouse` dialect | `_shared/platforms/fabric_lakehouse/dialect.md` | State how staging converts a dlt-landed UTC timestamp to the wall-clock value on Spark, as the DuckDB guidance gives `timezone('UTC', col)`. The onboarding templates ask the first staging model to prove it instead. | open |
| `generating-dlt-pipeline`, `fabric_lakehouse` dlt | `skills/generating-dlt-pipeline/SKILL.md`; `_shared/platforms/fabric_lakehouse/dlt.md` | State that `DLT_INGEST_LIMIT` bounds pages, not rows (carried over from the DuckDB repo's row for `duckdb_local/dlt.md`). | open |
| `onboarding` (repo draft) | `.agents/skills/onboarding/` | The draft is written for one platform at a time: this repo's copy is Fabric Lakehouse, the DuckDB repo's is DuckDB-local. Before it moves into the plugin, the platform-specific rows (profile, macros, orchestration, materialisation, SQL dialect) need a per-platform reference, as the plugin's `_shared/platforms/` does. | open |
| `install-ci` / `domain-cicd` `bundle_deploy.py` | `shared/scripts/bundle_deploy.py` (domain-cicd) | Deploying into a git worktree fails with `NotADirectoryError: ./.git/hooks`, because a worktree's `.git` is a file. Resolve the hooks directory with `git rev-parse --git-path hooks`. Tracked as VD-6929; this repo's bundle was deployed into a scratch repo and copied in without hooks. | open |
| `install-ci` / `domain-cicd` `validate_ci_config.py` | `domain-ci-fabric-bundle` `.github/scripts/validate_ci_config.py` | It passes the unfilled template (`<guid>`, `<string>`, `<domain-name>` placeholders), so a config the deploy cannot use reaches the first PR. Reject a value that is still a template placeholder. | open |
| `fabric_lakehouse` pipeline notebook | `_shared/platforms/fabric_lakehouse/pipeline-notebook.md` § Editing the generated cells | The Fabric Python runtime imports DuckDB 1.4.4 before the install cell runs, so installing `duckdb>=1.5.5` there changes the disk but not the kernel: code using a 1.5 API fails in Fabric and passes in the sandbox. Say which packages the runtime has already imported, and that code must run on those versions. Seen on 2026-10-19 as `'DuckDBPyConnection' object has no attribute 'to_arrow_table'`. | open |
| `domain-cicd` `deploy_orchestration.py` | `shared/scripts/deploy_orchestration.py` `parse_prod_manifest` | The `prod-target/manifest.json` it delivers to `Files/<slug>/transformation/` is parsed without the `+workspace_name` injection that `publish-prod-manifest.yml` applies, so its relation names are 3-part, and `source_defer.sql` refuses them under `--defer`. Studio's Intent cache uses the GitHub release (`manifest_prod.json`, 4-part), so that path is unaffected; a run that defers to the OneLake copy is not. Inject `workspace_name` as the publish does. | open |
| `install-ci` / `domain-cicd` Fabric bundle | `domain-ci-fabric-bundle/.github/profiles/profiles.yml`; `.github/workflows/{ci,publish-prod-manifest}.yml` | The bundle names its profile `dbt_fab_spark` and runs `dbt parse`/`compile` with `--profiles-dir .github/profiles` and no `--profile`, so a repo whose `dbt_project.yml` defaults to another profile name fails every gate and the manifest publish with "Could not find profile". `install-ci` should check the name, or the workflows should pass `--profile`. This repo renamed its profile to `dbt_fab_spark`. | open |
