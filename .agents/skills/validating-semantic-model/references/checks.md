# How the checker behaves

Read this when a gate surprises you. The rules live in
`../../semantic-model/references/modeling-rules.md`; this file explains what
the tool actually inspects, so a green or red result is not misread.

## Coverage of the checks

| Check | Reads | Does not read |
| --- | --- | --- |
| core validation | document structure, enums, references, `from_columns`/`to_columns`, SQL parses | `column_map` values, the repo's file list |
| VIBEDATA pass | key set per document component (metrics included), version consistency, LTS/source/alias references, grain/priority/column-map shape, levels (`keys` with exactly one primary and at most one display, attributes), `row_level` against the primary key and SCD, hierarchies against declared levels and `scd_rollup`, SCD field names, `from_columns` against declared fields, `content_levels`/`at_levels`/`time_series` against relationships and hierarchies, names in a `content_filter` (a `:placeholder` is an error) and its `held by` pointer, `derived_expression` inputs, that no column binds a derived, time-series or dimension-rule metric, one computation per metric and no cycles, a time-series or nested metric repeating its base expression, `FIRST`/`LAST` on a single time level | anything about meaning: honesty of a mapping, whether a filter matches the SQL, whether a level key is unique, population, additivity |
| values and expressions | every payload value against `vibedata-schema.json`'s constraints (identifiers, `schema.table` sources, the version, `join_type`, ISO dates, non-empty notes); each expression's kind (`predicate` or `metric-formula`: no aggregate, window or subquery); that a metric expression aggregates and a field expression does not; and, as a warning, any function outside Ossie's REQUIRED and RECOMMENDED lists (rules in `../../semantic-model/references/vibedata-fields.md` § "Values and expressions") | whether the predicate is the right one: a well-formed filter can still restate the wrong `WHERE` |
| cross-document drift | same-named datasets (`source`, keys, fields, `scd`, `hierarchies`, non-role logical sources including their content), metrics (expression and payload), physical tables (`source`, `dbt_model`, `table_type`, `alias_of`, `role`) | role logical sources and `note` text, which are local by design |
| `dimensionality` | per metric, the facts its expression reads and the dimensions reachable through many-to-one relationships and weighted bridges, derived metrics as the intersection of their inputs, `total` metrics as every dimension | queries: it reports reach, and the engine or exporter enforces it |
| `coverage` | dbt model file names (`*.sql`, recursively) under each boundary-layer root it is given vs `dbt_model` values; `--exclude` (the repo map's `semantic_exclusions`) waives a relation: `coverage/excluded` (info), or `coverage/excluded-but-mapped` (warning) when a `dbt_model` still names it | anything inside the SQL |
| `suppliers` | declared fields and metrics with no `column_map` entry anywhere; a derived, time-series or dimension-rule metric counts as supplied when its inputs are | whether the mapped column exists in the mart |
| `generate-tests` | the declared levels, hierarchies and aggregate content levels, turned into `assert_semantic_level_keys_hold` (severity `error`: a repeated row-level primary key, a key naming several members) and `assert_semantic_levels_hold` (severity `warn`: a member with several values of a key or several parents, an aggregate key value that is no member); and every aggregate binding of a metric, compiled twice (the source under its content filter, and the detail under the same filter) into `assert_semantic_content_holds`, which fails on any difference group by group at the source's content levels — full-joined for a navigable source, so a group either side lacks fails, and from the source's groups only for one that is not. A SUM reads a missing group as zero, and a decimal may differ by up to a cent. `--check` writes nothing and fails naming each stale or missing file | the data: the dbt tests read it. Whether a binding is the right business rule: equal groups prove the same population, not the right one |
| `columns` | every `column_map` target, aggregate `key_columns` and field-expression column against dbt's `catalog.json` (from `dbt docs generate` on a built warehouse); for a field that is one bare column, its `datatype` against the column's catalog type: a different class (text, number, temporal, boolean) is `columns/datatype-mismatch` (error), a different type in one class (`Decimal` over `DOUBLE`, `Date` over `TIMESTAMP`) the same code as a warning; an unrecognised warehouse type is not judged | whether the right column is mapped; the type of a computed field |
| `bindings` | for every aggregate logical source that binds a metric, the dbt model's compiled SQL from `manifest.json` (raw SQL when its only Jinja is `ref`/`source`), traced through CTEs, subqueries and `*` wrappers to the `SELECT` that aggregates each bound column: `bindings/aggregation-mismatch` (error) — a `SUM` metric over `AVG`, any `DISTINCT` aggregate, `MIN` or `MAX`, or over a column an inner `SELECT` aggregated that way; a `MIN`/`MAX` metric over anything else; `bindings/key-not-grouped` (error) — a content-level key the dbt model's final `SELECT` neither selects nor groups by (in an inner `SELECT` it is `bindings/unproven`, since a key may be renamed on the way out); `bindings/finer-than-declared` (warning) — it groups by a finer level's key of a content level's own dimension; `bindings/undeclared-filter` (warning) — it, or the CTE chain its rows come from (not a joined dimension), filters rows but the source declares no `content_filter`; `bindings/group-cut` (error) — the aggregating `SELECT` applies `HAVING`, a group-level cut that is no population of the detail, so the relation belongs in the repo map's `semantic_exclusions`, not in the Ossie documents; `bindings/unproven` (warning) — no SQL, or a column it cannot trace | whether a differently spelled filter is the same population (the content test compares that on data); window functions are not groupings; a combined expression (`sum(a)/count(b)`) is reported unproven, never judged |
| `compile` | one semantic query: the source chosen, the rejected sources with reasons, the SQL | anything it reports as unsupported, which it refuses rather than guesses |
| `notes` | `held by <test>` and `ADR NNNN` pointers in a source `note`, resolved against the singular tests and decision-record directories (`<test>.sql`, `NNNN-*.md`), and whether those directories exist | whether the test still tests what the note claims |
| ontology validation (`validate` on a `*.ontology.yaml`) | the vendored ontology schema, then the vendored reference pass (unique concept and relationship names; `extends`, `identify_by`, `roles` and QName prefixes resolving), then an `EntityType` with no `identify_by` (error) and declarations nothing evaluates — `requires`, `derived_by`, `prefixes`, `custom_extensions`, a concept's or relationship's `iri` (warnings) | whether a concept is the right concept, whether identity is natural, whether an expression is executable |
| mapping validation (`validate` on a `*.mapping.yaml`) | the vendored mapping schema, then `custom_extensions` as a declaration-only warning | anything across documents: `refs` reads that |
| `refs <ontology-dir> <model-dir>` | `ontology_ref` and `semantic_model_ref` names against document names; every mapped `concept` and `relationship` against the ontology (a relationship must belong to the concept it resolves, or one it extends); every `expression` as a `dataset.field` the referenced model declares; a model with no mapping (warning); and the identity lint below | whether an expression means what the mapping says, whether two mappings of one concept agree, coverage of the vocabulary |
| unmapped identity (part of `refs`) | `refs/unmapped-identity-dataset` (warning): a concept identified by one relationship is mapped on one dataset by `dataset.field`, and another dataset of the same document has a field of that name as its own `scd.natural_key`, level key or unversioned `primary_key`, yet no mapping of the concept names it. A foreign key is never a key of its dataset, so a fact is not flagged | whether that dataset really holds the concept's members or only shares a column name |
| identity lint (part of `refs`) | from the Ossie dataset's `scd`, `levels`, `row_level`, `primary_key` and relationship columns: `refs/identity-version-surrogate` — an identifying expression, or a link to an entity, names a versioned dataset's surrogate (`scd` type 2 or `row_level.versioned`, its `primary_key` and not its `scd.natural_key`) or a foreign key whose relationship targets one; `refs/identity-not-natural-key` — an object mapping's own identity names a field that is none of its dataset's `scd.natural_key`, a level's primary key or (unversioned) its `primary_key`, nor a foreign key onto one of those (always a warning); `refs/partial-identity` — a referent list maps only some of the relationships its concept's `identify_by` names | whether the declared natural key is the business's natural key, or whether a concept mapped onto another entity's dataset is the population it claims: a reviewer reads those |
| `glossary <ontology-dir> <context-md>` | `**Term**:` headings in the glossary against concept names, case-insensitively, both ways: `entity_types_without_term` (a finding: exit 1), `terms_without_concept` and `value_types_without_term` (reported for review, never fail) | whether a term denotes something with identity, or whether a reported term should become a concept |

## Behaviours worth knowing

- Cross-document comparison runs only when the directory holds more than one document.
- The VIBEDATA pass is skipped for a document that already fails the core checks, so fix core errors first.
- A missing `priority_group` defaults to `1`; nothing reports two detail-class sources.
- Every command prints JSON on stdout and exits 0 or 1: unreadable input, invalid YAML, a missing directory or a crashing check is a JSON error and exit 1, never a traceback.
- `validate` exits 1 only on structural errors. Warnings it emits are factual (for example `table-unjoined` — a table no join reaches, expected for an aggregate handle) and never fail the run.
- Unmatched files: a `*.y*ml` file in a validated directory that is not `*.ossie.yaml`, `*.ontology.yaml` or `*.mapping.yaml` is an error, so a mis-named document cannot be silently skipped.
- `validate` reads all three kinds and picks the schema from the document's own shape (`concept_mappings` → mapping, `ontology` → ontology, otherwise an Ossie document), so one directory can hold all three. The other Ossie-document commands (`coverage`, `suppliers`, `notes`, `generate-tests`, `columns`, `compile`, `dimensionality`) read `*.ossie.yaml` only, and refuse an ontology or mapping file passed directly (`cli/not-a-model`).
- A path that is not a directory where one is required (`refs`, `glossary`, a `coverage` root), or a file that parses to something other than a document (`cli/not-a-document`), is an error. A gate on a mistyped path never reports zero findings.
- `requires`, `derived_by`, `prefixes`, `custom_extensions` and a concept's or relationship's `iri` are warnings, never errors: the standard allows them, and nothing here evaluates them, so a document using them is declaration-only. A mapping's `ontology_ref`/`semantic_model_ref` `iri` is the schema's own and is never reported.
- `refs` takes directories, not files: identity is a claim across the ontology, the mapping and the Ossie document, so one document alone cannot answer it. It reports `mapping/none` per Ossie document with no mapping, as a warning pointing at that file; the reason goes in the document's description.
- The identity lint compares declarations only. It accepts a foreign key whose relationship lands on its target's natural key, and any level's primary key (a coarser level names a member too). `refs/identity-not-natural-key` is always a warning: a concept may legitimately be populated from a natural code held on another dataset (a degenerate key on a fact, a code held as an attribute), and no declaration says which dataset is the concept's, so the warning names the keys it compared against and a reviewer decides. `refs/identity-version-surrogate` and `refs/partial-identity` rest on declarations (`scd`, `row_level.versioned`, `identify_by`) and stay errors. Link mappings (`link_mappings`) get the reference checks, not the identity lint.
- `glossary` exits 1 only when an entity type has no term: an entity the glossary does not name is a vocabulary gap. A term with no concept, or a value type with no term, is listed for review and never fails the run.
- `notes` warns with `notes/no-directory` when the tests or decision-record directory is missing, so a clean run over an absent directory does not read as proof. Warnings never fail it; a dangling pointer does.
