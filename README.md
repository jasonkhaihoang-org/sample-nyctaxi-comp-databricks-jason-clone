# Sample NYC Taxi Analytics Domain — Databricks

A Databricks Domain for NYC taxi analytics, loaded by dlt and modelled in dbt. It
combines genuine NYC TLC trip records with two deterministically generated
source systems: a fleet operator's dispatch and telematics platform, and a
master-data platform.

The project exercises joins, sessionization, Type 2 dimensions, quality rules,
aggregate design and a semantic layer, without pretending that generated
driver, vehicle, garage or weather data is real. It is the Databricks
version of [`accelerate-data/sample-nyctaxi-comp`](https://github.com/accelerate-data/sample-nyctaxi-comp),
the DuckDB model-answer repo, ported from its Lakehouse version
[`accelerate-data/sample-nyctaxi-comp-fabric`](https://github.com/accelerate-data/sample-nyctaxi-comp-fabric),
and carries the same data product.

It is built as a model answer for a data product worked on by Vibedata agents:
conventions live in `AGENTS.md` and `.agents/skills/`, locations in
`repo-map.json`, decisions in `docs/adr/`, and a design record for each model and
pipeline in `docs/design/`.

## Data provenance

| Layer | Contents | Provenance |
| --- | --- | --- |
| `bronze` | Yellow/Green trips and the TLC zone lookup | Loaded verbatim by the `tlc` pipeline from the TLC site. dlt lands the source column names in lower case (`VendorID` as `vendorid`) and adds `_dlt_load_id` and `_dlt_id`. |
| `ops_raw` | Garages, vehicles, drivers, leases, shifts, trip assignments, status events, maintenance | Fully synthetic and deterministic, generated by the `ops` pipeline from the yellow trips. |
| `mdm_raw` | Zone, vendor, payment, rate, regime, borough, POI, calendar and weather masters | Mixed: some labels and rates are hand-transcribed; enriched attributes and weather are generated. |
| dbt models | Staging, intermediate, dimensions, facts, marts and aggregates | Derived transformations and business rules. |

Every layer is a schema in the Domain's Unity Catalog catalog, `nyctaxi_prod`. The TLC trip window is January
to March 2024. Read [`docs/setup/data-provenance.md`](docs/setup/data-provenance.md)
before treating a result as a real-world claim. Trip-level TLC facts are
genuine; Harbour Point identities and operational outcomes are not.

## Architecture

```text
TLC site ──► ingestion/tlc_pipeline.ipynb ──► bronze ────────────────┐
                    │                                                  │
                    ├─► ingestion/ops_pipeline.ipynb ──► ops_raw ──────┤
                    └─► ingestion/mdm_pipeline.ipynb ──► mdm_raw ──────┤
                                                                       ▼
                dbt (dbt-databricks): staging → intermediate → marts (core, agg, finance, ops)
                                                                       │
                                                                       ▼
                                              semantic model (MetricFlow) and dbt docs
```

The `nyc_taxi_refresh` Lakeflow job (`orchestration/nyc_taxi_refresh.job.yml`,
included by the Declarative Automation Bundle `databricks.yml`) runs the three
pipeline notebooks, then a dbt task that runs `dbt build` on the Domain's SQL
warehouse. Each pipeline notebook loads Delta tables through the
`databricks_files_api()` destination. dbt reads and writes the same catalog.

## Repository layout

- `ingestion/`: one dlt pipeline notebook per source (`<name>_pipeline.ipynb`), their source code under `sources/`, resource docs and `.dlt/config.toml`.
- `databricks.yml` and `orchestration/`: the bundle and the Lakeflow job it deploys.
- `transformation/`: the dbt project (staging, intermediate, marts, seeds, macros, tests).
- `tests/`: pytest tests for ingestion and the maps.
- `repo-map.json` and `test-map.json`: where things are, and which tests protect them.
- `AGENTS.md` and `.agents/skills/`: how to work in this repo.
- `CONTEXT.md`: the vocabulary of the data product.
- `docs/adr/` and `docs/design/`: decisions, and design records per model and pipeline.
- `docs/setup/`: repo maintenance: the port's requirements and plan, the skill changes it implies, data provenance and Domain seeding.
- `docs/proposal/pending-requests.md`: requests from the driver ops team for the Queens office launch.
- `docs/requirement/`: requirements for past work.
- `.github/` and `.workflow/`: Domain CI. The Databricks CI bundle publishes the production manifest; it runs no PR gates.

## Prerequisites

- A Databricks workspace with Unity Catalog, holding the Domain's catalog and a SQL warehouse, and serverless compute for the pipeline notebooks and the job.
- A Databricks-backed secret scope as the Domain's secret store.
- Python 3.12 for the offline tests:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt
```

There is no local warehouse file. Data lives only in Databricks.

## Seeding a Domain

To build a Domain that Studio Intents can work against, see
`docs/setup/seeding-the-domain.md`. A Domain is released once (data loaded,
every model built, production manifest published), and each Intent's sandbox
defers to it: an Intent writes its own schemas in the Domain's shared Ephemeral
catalog, each named with the Intent's prefix (`ephm__<domain>__<intent>__`),
builds only the models it changes, and reads everything else from the Domain.

## dbt targets and model layers

In a Studio Intent the runtime renders the profile `dbt_databricks` and its one
target, `databricks_sandbox`, which writes the Intent's schemas in the Ephemeral
catalog. `transformation/profiles.yml` holds the `prod` target on the Domain's
catalog, `nyctaxi_prod`, used by a release. Every layer sets its own schema, so
a sandbox builds `staging` as `<prefix>staging`, `core` as `<prefix>core`, and
so on. Every model is a table, by choice: one rule for every layer. The project
is organised as:

- **staging**: one model per source table, renamed and typed.
- **intermediate**: conformed trip, status, occupancy, fare and quality logic.
- **core marts**: dimensions, bridges and facts, plus the semantic model.
- **aggregates**: driver, vehicle, zone, OD, weather and occupancy summaries.
- **finance marts**: daily revenue, monthly summaries and revenue bridges.
- **operations marts**: driver, vehicle and trip-quality scorecards.
- **seeds**: four analyst-owned banding tables.

The reporting window (`2024-01-01` through `2024-04-01`) and the billable-trip
definition live in dbt models and project variables. They are not applied when
bronze is loaded.

## Tests and validation

```bash
python3 -m pytest tests -q    # offline: ingestion sources, the maps, ADR links
ruff check .
```

dbt data and unit tests run against Databricks, inside an Intent or after a
release; `test-map.json` says which command protects which layer.

## Important limitations

- `ops_raw` driver, vehicle, garage, lease, maintenance and weather records are
  synthetic and are not real NYC operations.
- Generated zone coordinates, population, area, demand tiers and version
  histories are plausible-looking test attributes, not authoritative geography.
- Re-running the ingestion replaces the loaded tables.
